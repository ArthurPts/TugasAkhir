PHASE 1 — FIX BLOCKING INCONSISTENCIES
===========================================================

Tujuan:
Membersihkan bug yang dapat menyebabkan implementasi/test Fase 5-6 gagal.

1. FIX `start_time`

Masalah:
`chord_placements` hanya memiliki:
- position
- start_beat

Tetapi kode menggunakan:
- ChordPlacement::$fillable -> start_time
- SongFactory -> start_time
- ChordPlacementController store/update -> start_time

Tugas:
- Hapus penggunaan `start_time` jika tidak termasuk desain final.
- Sesuaikan `$fillable`.
- Hapus `start_time` dari factory.
- Hapus validasi/request field `start_time`.
- Pastikan controller hanya menggunakan `position` dan/atau `start_beat` sesuai spesifikasi.
- Jangan menambahkan kolom `start_time` hanya untuk membuat kode lama lolos.

2. FIX TTS VOICE CONFIGURATION

Masalah:
Job/controller menerima `voice` dari client dan memakai hardcoded:
`en-US-AriaNeural`

Desain final:
- satu voice tetap
- dikonfigurasi dari `.env`
- tidak ada parameter voice per request

Tugas:
- Pastikan `config/services.php` memiliki konfigurasi TTS default voice.
- Tambahkan/pertahankan `.env.example`, misalnya:
  TTS_DEFAULT_VOICE=...
- `GenerateChordAudioJob` mengambil voice dari config.
- Hapus parameter `$voice` dari constructor job jika tidak diperlukan.
- Hapus `voice` dari query/request client.
- Pastikan semua pemanggilan job memakai configured voice.
- Jangan membuat variasi file audio berdasarkan voice request.

3. FIX TIME SIGNATURE FALLBACK

Aturan:
`time_signature_numerator` harus fallback ke 4 bila null.

Tugas:
- Di `buildTimelineResponse()` gunakan fallback 4.
- Audit semua kalkulasi beat/bar yang memakai numerator.
- Pastikan fallback diterapkan konsisten.
- Jangan mengubah nilai database secara otomatis hanya karena null.

Acceptance criteria:
- Factory tidak lagi menghasilkan `start_time`.
- Request chord placement dengan `start_time` tidak menjadi bagian API final.
- Tidak ada SQL query yang mengakses kolom `start_time`.
- Client tidak bisa memilih voice TTS.
- Voice berasal dari config.
- Timeline selalu memiliki numerator valid, minimal fallback 4.
- Existing Tahap 1-4 tests tetap pass.

PHASE 2 — DOMAIN SERVICE §5.1
COORDINATE CONVERSION + COLLISION
===========================================================

Tujuan:
Implementasikan inti Fase 5b sebelum membuat UI editor.

Buat service khusus, misalnya:
`ChordPlacementCoordinateService`
atau nama domain-equivalent yang konsisten dengan repository.

Tanggung jawab:
1. Konversi:
   - position -> start_beat
   - start_beat -> position
2. Validasi input.
3. Collision detection.
4. Force override sesuai spesifikasi.
5. Jangan mengubah data secara otomatis tanpa aturan yang ditentukan.

Aturan:
- Tentukan satu definisi resmi hubungan `position` dan `start_beat` berdasarkan spesifikasi.
- Jangan membuat rumus baru berdasarkan asumsi.
- Perhitungkan time signature/bar bila memang diwajibkan spesifikasi.
- Gunakan integer/decimal precision yang konsisten.
- Hindari floating point comparison yang rawan error bila domain membutuhkan presisi.

Collision:
- Jika placement baru bertabrakan dengan placement lain pada posisi/beat yang sama sesuai definisi spesifikasi:
  return HTTP 409 Conflict.
- Response harus memberi informasi yang cukup kepada client untuk mengetahui collision.
- Jika `force` diperbolehkan:
  - hanya lakukan override jika eksplisit diminta client
  - jangan mengaktifkan force secara default
- Pastikan placement milik lagu yang sama.
- Saat update, exclude record dirinya sendiri dari collision query.

Concurrency:
- Gunakan transaction bila operasi melibatkan read-check-write.
- Bila diperlukan oleh DB, pertimbangkan locking untuk mencegah race condition.

Controller:
`ChordPlacementController@store`
`ChordPlacementController@update`
harus memakai service tersebut.

Acceptance criteria:
- POST placement menggunakan coordinate yang ditentukan spec dapat menghasilkan coordinate pasangan secara otomatis.
- PATCH placement juga melakukan konversi.
- Collision menghasilkan 409.
- `force` bekerja hanya jika eksplisit.
- Tidak ada duplicate placement yang lolos hanya karena request datang bersamaan.
- Unit test tersedia untuk:
  - conversion
  - collision
  - update sendiri
  - force
  - invalid coordinate

PHASE 5 — §5.4 COUNT-IN + PLAYER TIMING
===========================================================

Tujuan:
Memperbaiki timing player agar count-in benar-benar terjadi sebelum lagu.

Masalah saat ini:
Metronom, chord dan backing track mulai bersamaan.

Implementasi:
1. Definisikan:
   - countInBars
   - countInBeats
   - songStartTime
2. Gunakan:
   `countInBeats = countInBars * time_signature_numerator`
3. Hitung durasi beat:
   `60 / BPM`
4. Jadwalkan metronom count-in terlebih dahulu.
5. `songStartTime` terjadi setelah count-in selesai.
6. Jadwalkan:
   - backing track
   - chord TTS
   - metronome song beats
   berdasarkan `songStartTime`.
7. Jangan menggunakan setTimeout sebagai satu-satunya mekanisme timing presisi bila Web Audio scheduling dapat digunakan.
8. Pastikan semua source menggunakan shared audio clock.
9. Pastikan pause/resume/stop tetap konsisten jika fitur tersebut sudah ada.

TTS:
- Jangan generate audio baru karena client mengirim voice.
- Gunakan audio hasil voice default configured.

Acceptance criteria:
- Count-in terjadi satu bar sebelum chord/backing track.
- Untuk 4/4 dan BPM 120, count-in berlangsung 2 detik.
- Untuk 3/4 dan BPM 120, count-in berlangsung 1.5 detik.
- Chord pertama dimulai pada beat 1 setelah count-in.
- Backing track tidak mulai sebelum songStartTime.
- Metronome tidak kehilangan sinkronisasi.

AGENT BEHAVIOR SAAT MENEMUKAN MASALAH
===========================================================

Jika agent menemukan masalah tambahan:

1. Jika blocker:
   - berhenti pada tahap aktif
   - jelaskan file, error, root cause
   - perbaiki jika masih berada dalam scope tahap tersebut.

2. Jika non-blocker:
   - jangan melakukan refactor besar.
   - catat sebagai follow-up.
   - lanjutkan tahap aktif bila acceptance criteria tetap dapat diverifikasi.

3. Jika spesifikasi ambigu:
   - inspect kode/spec lain terlebih dahulu.
   - cari implementation pattern yang sudah digunakan.
   - jangan mengarang behavior baru.
   - jika tetap ambigu dan berdampak pada database/API contract, minta keputusan manusia sebelum membuat breaking change.

4. Setiap perubahan:
   - tampilkan ringkasan file yang diubah.
   - tampilkan test yang dijalankan.
   - tampilkan hasil test.
